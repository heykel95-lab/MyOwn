\chapter{Controller Design and Real-Time Implementation}
\label{ch:implementation}

This chapter describes the real-time implementation of the Cartesian impedance
controller developed in \mbox{\Cref{ch:theory}}. The implementation combines
surface-relative geometry, phase-dependent reference generation, a selectable
virtual \abbr{CoC}, null-space control, and real-time data handling.
Mathematical relations already established in \mbox{\Cref{ch:theory}} are
referenced here rather than restated, so that this chapter carries only what
the controller adds to them. The controller is written in C++ using libfranka
and Eigen and is executed through the Franka Control Interface
(\mbox{\abbr{FCI}}) at a nominal control period of \mbox{\(1\,\mathrm{ms}\)}.
Numerical settings used in the experiments are given in
\mbox{\Cref{ch:methodology}} and \mbox{\Cref{app:controller_parameters}}.


\section{Controller Architecture and Real-Time Control Cycle}
\label{sec:software_architecture}
\label{sec:real_time_control_loop}

The software separates configuration and operator interaction from the
real-time control calculation and from post-run data processing. The complete
parameter set is read and validated before a controller session starts, so the
real-time callback receives only the prepared configuration, preallocated
state, the robot-model interface, and non-blocking operator requests. File
output and run evaluation are performed after torque control has stopped.

At program start the \mbox{\abbr{FCI}} connection is established, error
recovery is requested, the selected collision behaviour is applied, and the
robot model is loaded. A separate keyboard thread receives operator requests
and transfers them through atomic variables, which keeps terminal input outside
the real-time callback. Reading and validating the configuration again before
each session permits settings to be changed between runs without recompiling.

\begin{figure}[H]
  \centering
  \resizebox{\textwidth}{!}{\input{figures/controller_block_diagram.tex}}
  \caption{Torque contributions combined in one control cycle.}
  \label{fig:controller_block_diagram}
\end{figure}

\mbox{\Cref{fig:controller_block_diagram}} shows the torque path of one
impedance-controlled cycle, and the order within that cycle is fixed. The
callback first reads the measured joint configuration \mbox{\(q\)}, the joint
velocity \mbox{\(\dot q\)}, the end-effector pose, the \mbox{\(6\times7\)}
geometric Jacobian \mbox{\(J(q)\)}, and the remaining robot-model quantities.
The phase logic then updates the desired Cartesian reference. The Cartesian
pose error and the impedance wrench \mbox{\(F=[f^\top,m^\top]^\top\)} are
evaluated according to \mbox{\Cref{subsec:cartesian_pose_error}} and
\mbox{\Cref{sec:cartesian_impedance_control}}, using the reference of the
active phase and the impedance matrices selected for it. That wrench is mapped
to joint torque through \mbox{\(J^\top(q)\)}, the secondary null-space torque
and the model Coriolis contribution are added, the required signals are stored
in preallocated memory, and the resulting torque vector is returned to
libfranka.

The end-effector pose supplied by the robot state is used directly for
\mbox{\(p_{\mathrm{EE}}\)} and \mbox{\(R_{\mathrm{EE}}\)}. The real-time
controller does not reconstruct that pose from a separate
Denavit--Hartenberg chain.

Two properties of the error evaluation belong to the implementation rather
than to the impedance law. A rotational mask can be applied by resolving
\mbox{\(e_R\)} in the surface frame, retaining the enabled components, and
transforming the result back to the base frame; the mask acts on the
rotational spring error alone, while the damping term continues to use the
measured angular velocity. The controller also carries two impedance branches,
one decoupled and one shifted to a virtual \abbr{CoC}, and the active phase
selects between them.

The complete impedance-controlled command is

\begin{equation}
\tau_{\mathrm{cmd}}
=
J^\top(q)F
+
\tau_{\mathrm{null}}
+
\tau_c(q,\dot q).
\label{eq:implementation_callback_torque_command}
\end{equation}

Here \mbox{\(\tau_{\mathrm{null}}\)} is the secondary null-space torque of
\mbox{\Cref{subsec:complete_nullspace_torque}} and
\mbox{\(\tau_c(q,\dot q)\)} is the Coriolis and centrifugal contribution
obtained from the libfranka model. No separate gravity term is added, because
the \mbox{\abbr{FCI}} compensates gravity for the external joint-torque
command, as described in \mbox{\Cref{subsec:coriolis_gravity_compensation}}. An
experiment-specific disturbance torque is added only for the null-space
pose-hold experiment of \mbox{\Cref{sec:nullspace_hold_study}} and is therefore
not part of the nominal controller formulation.

The implemented controller is used in two configurations in this thesis. The
surface-contact configuration generates a phase-dependent Cartesian reference
for tool orientation, surface approach, contact set-up and the subsequent
grinding phase. The Cartesian pose-hold configuration instead captures and
maintains a fixed Cartesian pose, and it carries the separate null-space
investigation of \mbox{\Cref{sec:nullspace_hold_study}}. Both run the callback
above, and they differ in the reference they generate and in the impedance they
activate. Each is described in full before the other begins.


\section{Surface-Contact Sequence}
\label{sec:implemented_configurations}
\label{subsec:implementation_contact_sequence}
\label{sec:control_phases}

A surface-contact run passes through four phases, drawn in
\mbox{\Cref{fig:phase_flow_chart}}. The step between approach and set-up is a
transition rather than a fifth phase. It occurs when the geometric clearance of
the tool face reaches its configured threshold. The quantities that initialise
the set-up reference are captured at that instant.

\begin{figure}[H]
  \centering
  \input{figures/phase_flow_chart.tex}
  \caption{Surface-contact phase sequence.}
  \label{fig:phase_flow_chart}
\end{figure}

\begin{itemize}
  \item Tool orientation moves the tool to the commanded surface-relative
        angular offset while the captured TCP position is held.
  \item Surface approach retains that orientation and advances the position
        reference towards the surface along \mbox{\(-n_s\)}. The phase ends at
        the clearance transition, where the pose and the selected tool-point
        offset used to initialise set-up are captured.
  \item Contact set-up presses the selected tool point onto the surface while
        the captured orientation is held. Contact-induced end-effector rotation
        and the optional compliance-centre coupling act in this phase.
  \item Grinding retains the normal press and superimposes a tangential
        motion. No reported run entered it.
\end{itemize}

A phase is a generated Cartesian reference together with an active impedance
configuration, and the four fall into two gain groups. Tool orientation and
surface approach share the first. Contact set-up uses the compliant contact
gains and can activate the shifted virtual \abbr{CoC}, while grinding retains
those source gains and returns to the decoupled Cartesian impedance.
\mbox{\Cref{subsec:implementation_setup_phase}} gives the construction, and
the numerical values are stated in \mbox{\Cref{ch:methodology}}. The
subsections below follow the sequence in the order the controller executes it.


\subsection{Surface and Tool Reference}
\label{subsec:implemented_surface_task_frame}
\label{sec:tool_orientation_given_surface}
\label{sec:surface_task_plane}

The sequence requires a frame for resolving the surface-relative directions,
an orientation target for the tool face, and a geometric representation of the
rectangular tool face. These quantities are defined below.

The controller constructs the surface frame according to
\mbox{\Cref{subsec:surface_task_frame}} from a configured surface point
\mbox{\(p_s\)}, the surface orientation, and a configured first-tangent hint.
That hint is the in-plane reference direction of
\mbox{\Cref{subsec:surface_task_frame}} and is a parameter rather than a fixed
axis, so a fallback direction is applied when the configured one lies close to
\mbox{\(n_s\)}. The resulting directions
\mbox{\(t_1\)}, \mbox{\(t_2\)} and \mbox{\(n_s\)} are then used consistently
for the descent direction \mbox{\(-n_s\)}, the surface-relative orientation
command, the directional Cartesian gains, the compliance-centre definition
when a surface-fixed displacement is selected, and the surface-resolved
quantities of the experimental evaluation.

The tool normal is calibrated once in the end-effector frame. Its current
direction in the base frame follows from the measured end-effector
orientation:

\begin{equation}
n_{\mathrm{Tool},0}=R_{\mathrm{EE}}n_{\mathrm{Tool,EE}}.
\label{eq:implementation_current_tool_normal}
\end{equation}

The commanded orientation offset about the two surface tangents is represented
by the rotation vector

\begin{equation}
\theta_{\mathrm{cmd}}
=
\theta_{t_1}t_1
+
\theta_{t_2}t_2
\in\mathbb{R}^3.
\label{eq:implementation_tilt_rotation_vector}
\end{equation}

Its magnitude \mbox{\(\lVert\theta_{\mathrm{cmd}}\rVert\)} is the commanded
offset angle. For a non-zero offset the corresponding unit rotation axis is

\begin{equation}
u_{\mathrm{cmd}}
=
\frac{\theta_{\mathrm{cmd}}}{\lVert\theta_{\mathrm{cmd}}\rVert},
\label{eq:implementation_commanded_rotation_axis}
\end{equation}

and the axis--angle relation of \mbox{\Cref{eq:rodrigues_formula}} gives the
commanded rotation matrix
\mbox{\(R_{\mathrm{cmd}}=R(u_{\mathrm{cmd}},\lVert\theta_{\mathrm{cmd}}\rVert)\)},
which is the identity for a zero commanded offset. This single vector covers
the conditions the experiments use: an offset about \mbox{\(t_1\)} alone, an
offset about \mbox{\(t_2\)} alone, and the intermediate tangent-plane
directions.

Since \mbox{\(n_s\)} points out of the surface, the tool-normal direction for
a tool face parallel to the surface is \mbox{\(-n_s\)}. Applying the
commanded orientation offset to that direction gives the desired tool-normal
direction

\begin{equation}
n_d
=
R_{\mathrm{cmd}}\left(-n_s\right).
\label{eq:implementation_tool_normal_target}
\end{equation}

For a zero commanded offset \mbox{\(n_d=-n_s\)}. The shortest rotation that aligns the captured tool
direction with \mbox{\(n_d\)} is applied to the complete start orientation.
The implementation can additionally prescribe a twist about the desired tool
axis, which fixes the in-plane orientation of the rectangular face; because a
centred rectangle is unchanged by a half-turn, the equivalent orientation
closest to the captured start pose is selected. The settings used for the
measurements are stated in \mbox{\Cref{ch:methodology}}.


\label{sec:tool_contact_geometry}%
Surface approach cannot be decided from the TCP height alone, because a face
that is not parallel to the surface reaches the plane first at a corner or
along an edge. The tool face is therefore represented as a rectangle fixed in
the end-effector frame.
Its centre offset, half-width vector, and half-length vector define the four
end-effector-frame corner offsets \mbox{\(r_{i,\mathrm{EE}}\)},

\begin{equation}
r_{i,\mathrm{EE}}\in
\left\{
r_{\mathrm{face,EE}}
\mathbin{\pm}r_{\mathrm{width,EE}}
\mathbin{\pm}r_{\mathrm{length,EE}}
\right\}.
\label{eq:implementation_tool_face_vertices}
\end{equation}

The offsets are defined from the tool centre point, which coincides with the
reported end-effector origin in this implementation,
\mbox{\(p_{\mathrm{TCP}}=p_{\mathrm{EE}}\)}. During surface approach the four
corners determine the minimum tool clearance and the contact reference used
for set-up, as described in
\mbox{\Cref{subsec:implementation_clearance_detection}}.

\subsection{Tool Orientation}
\label{subsec:implementation_tool_orientation_phase}

The tool-orientation phase holds the captured start position while the desired
orientation is advanced towards the surface-relative target of
\mbox{\Cref{eq:implementation_tool_normal_target}}, following a rate-limited
interpolation from the captured start orientation. Its transition is evaluated
from the tool-axis error and, when the in-plane twist is enabled, the
remaining spin error about the target tool axis. A configured minimum duration
prevents immediate acceptance of a transient orientation, and a timeout
supplies an alternative transition path. The measured orientation at this
transition is the orientation from which descent begins, and it remains the
desired orientation throughout the approach that follows.

\subsection{Surface Approach, Clearance and Tool-Point Selection}
\label{subsec:implementation_surface_approach_phase}
\label{subsec:implementation_clearance_detection}

Surface approach advances the TCP towards the plane along
\mbox{\(-n_s\)}. Its scalar coordinate \mbox{\(s_{\mathrm{app}}(t)\)} is
the commanded travel from the TCP position \mbox{\(p_{\mathrm{TCP,start}}\)}
captured when the phase begins at \mbox{\(t_{\mathrm{app},0}\)},

\begin{equation}
s_{\mathrm{app}}(t)
=
\begin{cases}
v_{\mathrm{app}}\left(t-t_{\mathrm{app},0}\right),
& t_{\mathrm{app},0}\leq t<t_{\mathrm{app,max}},\\[4pt]
s_{\mathrm{app,max}}, & t\geq t_{\mathrm{app,max}},
\end{cases}
\label{eq:implementation_approach_coordinate}
\end{equation}

with the configured descent speed \mbox{\(v_{\mathrm{app}}\)}, the
configured maximum descent distance \mbox{\(s_{\mathrm{app,max}}\)}, and
\mbox{\(t_{\mathrm{app,max}}\)} the instant at which the ramp reaches that
distance. Both configured values are listed in
Table~\ref{tab:experimental_phase_parameters}, and the saturation bounds an
approach that does not reach the clearance threshold. The desired TCP
position follows as

\begin{equation}
p_d(t)=p_{\mathrm{TCP,start}}-s_{\mathrm{app}}(t)n_s,
\label{eq:implementation_approach_reference}
\end{equation}

During the linear approach, the desired TCP velocity is
\mbox{\(\dot p_d(t)=-v_{\mathrm{app}}n_s\)}. Reaching
\mbox{\(s_{\mathrm{app,max}}\)} before the clearance criterion is satisfied
terminates the approach as unsuccessful.
Where the tool face is not parallel to the surface, the corner closest to the
plane can lie well below the TCP, so the TCP height alone does not give the
clearance the transition needs. The
controller therefore evaluates the four corners of
\mbox{\Cref{fig:face_feature_selection}} in every control cycle. Their
positions and clearances also identify the point of the face that set-up should
press onto the surface.

The base-frame position \mbox{\(p_i(t)\)} of tool-face corner \mbox{\(i\)} is

\begin{equation}
p_i(t)
=
p_{\mathrm{TCP}}(t)+R_{\mathrm{EE}}(t)r_{i,\mathrm{EE}}.
\label{eq:implementation_corner_position}
\end{equation}

Its signed clearance \mbox{\(h_i(t)\)} from the calibrated surface is

\begin{equation}
h_i(t)
=
n_s^\top\left(p_i(t)-p_s\right).
\label{eq:implementation_corner_clearance}
\end{equation}

Smaller values of \mbox{\(h_i\)} place a corner closer to the surface. Since
\mbox{\(p_{\mathrm{TCP}}\)} and \mbox{\(p_s\)} are common to all four
corners, comparing the clearances \mbox{\(h_i\)} is equivalent to comparing
the rotated corner offsets along the surface approach direction. The
implementation uses this equivalent form for the corner comparison.

The minimum tool clearance \mbox{\(h_{\mathrm{Tool}}(t)\)} is the minimum
signed clearance between the rectangular tool face and the calibrated
surface, evaluated from its four corners:

\begin{equation}
h_{\mathrm{Tool}}(t)
=
\min_{i\in\{1,2,3,4\}}h_i(t).
\label{eq:implementation_tool_clearance}
\end{equation}

The phase ends at the clearance transition, where

\begin{equation}
h_{\mathrm{Tool}}(t)\leq h_{\mathrm{clearance}},
\label{eq:implementation_clearance_transition}
\end{equation}

with \mbox{\(h_{\mathrm{clearance}}\)} the configured tool clearance of
Table~\ref{tab:experimental_phase_parameters}. The approach trajectory is
generated for the TCP, whereas the transition to set-up is determined from the
physical tool geometry. Since \mbox{\(h_{\mathrm{Tool}}\)} is the minimum
clearance of the four tool-face corners,
\mbox{\(h_{\mathrm{clearance}}\)} refers to the part of the rectangular
tool face closest to the plane rather than to the TCP. For the reported value
\mbox{\(h_{\mathrm{clearance}}=0.020\,\mathrm{m}\)}, this part of the
tool face is \mbox{\(20\,\mathrm{mm}\)} above the calibrated plane at the
transition. The criterion therefore provides the same specified tool clearance
for different tool orientations and is purely geometric.

At the clearance transition, the same four clearances determine the selected
tool point used for set-up. A corner belongs to the selected index set
\mbox{\(\mathcal I_{\mathrm{sel}}\)} when its clearance differs from the
closest corner by no more than the tool-point selection tolerance
\mbox{\(\varepsilon_{\mathrm{sel}}\)}:

\begin{equation}
\mathcal I_{\mathrm{sel}}
=
\left\{
i\in\{1,2,3,4\}
\;\middle|\;
h_i-h_{\mathrm{Tool}}\leq\varepsilon_{\mathrm{sel}}
\right\}.
\label{eq:implementation_selected_corner_set}
\end{equation}

The tolerance is recorded in \mbox{\Cref{tab:calibrated_tool_geometry}}. The
principal geometric cases contain one selected corner, two neighbouring
selected corners, or all four corners. These give the leading corner, the
leading-edge midpoint, and the tool-face centre, respectively. With
\mbox{\(N=\lvert\mathcal I_{\mathrm{sel}}\rvert\)}, the selected tool-point
offset \mbox{\(r_{\mathrm{Tool,EE}}\)} is the mean of the selected corner
offsets,

\begin{equation}
r_{\mathrm{Tool,EE}}
=
\frac{1}{N}\sum_{i\in\mathcal I_{\mathrm{sel}}}r_{i,\mathrm{EE}}.
\label{eq:implementation_leading_feature_average}
\end{equation}

The selected tool point \mbox{\(p_{\mathrm{Tool}}\)} is the geometric contact
reference used during set-up. Its position is

\begin{equation}
p_{\mathrm{Tool}}=p_{\mathrm{TCP}}+R_{\mathrm{EE}}r_{\mathrm{Tool,EE}}.
\label{eq:implementation_contact_point_position}
\end{equation}

The principal geometric cases are shown in
\mbox{\Cref{fig:leading_feature_cases}}. For the tool-face centre,
\mbox{\(r_{\mathrm{Tool,EE}}=r_{\mathrm{face,EE}}\)}. That calibrated offset
lies along the end-effector \mbox{\(z\)}-axis, so the selected tool point then
sits on that axis directly beneath the TCP.

\begin{figure}[H]
  \centering
  \input{figures/leading_feature_cases.tex}
  \caption[Principal selected tool points for the rectangular tool face.]{%
    Principal selected tool points for the rectangular tool face: leading
    corner, leading-edge midpoint, and tool-face centre.}
  \label{fig:leading_feature_cases}
\end{figure}

The minimum clearance \mbox{\(h_{\mathrm{Tool}}\)} determines when approach
ends. The offset \mbox{\(r_{\mathrm{Tool,EE}}\)} determines which physical
tool point the set-up reference uses. At the clearance transition the selected
offset is retained in end-effector coordinates and then held constant
throughout set-up.

Three points remain distinct in this construction. The impedance law regulates
the Cartesian reference point \mbox{\(p_{\mathrm{TCP}}\)}. The selected tool
point \mbox{\(p_{\mathrm{Tool}}\)} belongs to the physical tool geometry, and
its base-frame offset
\mbox{\(r_{\mathrm{Tool}}=R_{\mathrm{EE}}r_{\mathrm{Tool,EE}}=p_{\mathrm{Tool}}-p_{\mathrm{TCP}}\)}
changes with the tool orientation. The virtual \abbr{CoC} \mbox{\(p_c\)} of
\mbox{\Cref{sec:centre_of_compliance}} is a software-defined impedance
reference and carries no tool geometry.

With the optional pre-set-up gate enabled, the captured pose is held until
operator confirmation, and the set-up references are then captured from the
current measured state.

\subsection{Contact Set-Up}
\label{subsec:implementation_setup_phase}
\label{sec:surface_frame_gains}
\label{subsec:phase_dependent_gain_construction}
\label{subsec:inertia_scaled_damping_calculation}

In the reported surface-contact runs, set-up begins directly at the clearance
transition. Its Cartesian reference is constructed from the selected tool
point and end-effector pose captured at that instant. The captured orientation
\mbox{\(R_{\mathrm{EE,clearance}}\)} and TCP position
\mbox{\(p_{\mathrm{TCP,clearance}}\)} are taken at the clearance-transition
instant \mbox{\(t_{\mathrm{set},0}\)},

\begin{equation}
R_{\mathrm{EE,clearance}}=R_{\mathrm{EE}}(t_{\mathrm{set},0}),
\qquad
p_{\mathrm{TCP,clearance}}=p_{\mathrm{TCP}}(t_{\mathrm{set},0}).
\label{eq:implementation_clearance_pose}
\end{equation}

The corresponding selected tool-point position
\mbox{\(p_{\mathrm{Tool,clearance}}\)} is

\begin{equation}
p_{\mathrm{Tool,clearance}}
=p_{\mathrm{TCP,clearance}}+R_{\mathrm{EE,clearance}}r_{\mathrm{Tool,EE}}.
\label{eq:implementation_clearance_tool_point}
\end{equation}

Its orthogonal projection onto the calibrated surface plane defines the
surface reference point \mbox{\(p_{\mathrm{Tool},0}\)},

\begin{equation}
p_{\mathrm{Tool},0}
=p_{\mathrm{Tool,clearance}}
-n_sn_s^\top\left(p_{\mathrm{Tool,clearance}}-p_s\right).
\label{eq:implementation_projected_tool_point}
\end{equation}

\mbox{\(p_{\mathrm{Tool},0}\)} is therefore the point on the calibrated
plane directly below the selected tool point at the clearance transition.

Set-up generates the contact press evaluated in the experiments. The scalar
coordinate \mbox{\(s_{\mathrm{set}}(t)\)} gives the selected tool point's
commanded displacement from \mbox{\(p_{\mathrm{Tool},0}\)} towards the surface.
Its initial value is the negative signed surface coordinate of that point,

\begin{equation}
s_{\mathrm{set}}(t_{\mathrm{set},0})
=
-n_s^\top\left(p_{\mathrm{Tool,clearance}}-p_s\right).
\label{eq:implementation_setup_initial_coordinate}
\end{equation}

The selected point remains above the surface at the transition, so
\mbox{\(s_{\mathrm{set}}(t_{\mathrm{set},0})<0\)}. This initial value makes
the first set-up reference equal to \mbox{\(p_{\mathrm{Tool,clearance}}\)} and avoids
a position step.

The coordinate advances at the configured press speed
\mbox{\(v_{\mathrm{set}}\)} from \mbox{\(t_{\mathrm{set},0}\)} until it reaches
the configured endpoint \mbox{\(s_{\mathrm{set,max}}\)}, then remains constant:

\begin{equation}
s_{\mathrm{set}}(t)
=
\begin{cases}
s_{\mathrm{set}}(t_{\mathrm{set},0})
+v_{\mathrm{set}}\left(t-t_{\mathrm{set},0}\right),
& t_{\mathrm{set},0}\leq t<t_{\mathrm{set,max}},\\[4pt]
s_{\mathrm{set,max}}, & t\geq t_{\mathrm{set,max}}.
\end{cases}
\label{eq:implementation_setup_press_coordinate}
\end{equation}

The desired selected-tool-point position \mbox{\(p_{\mathrm{Tool},d}(t)\)} is

\begin{equation}
p_{\mathrm{Tool},d}(t)
=
p_{\mathrm{Tool},0}-s_{\mathrm{set}}(t)n_s.
\label{eq:implementation_setup_face_point_reference}
\end{equation}

\mbox{\Cref{app:controller_parameters}} records the configured press speed and
endpoint.

Throughout set-up the desired orientation is

\begin{equation}
R_d(t)=R_{\mathrm{EE,clearance}}.
\label{eq:implementation_setup_orientation_reference}
\end{equation}

The set-up trajectory is defined for the selected physical tool point, whereas
the Cartesian impedance law regulates the TCP. The desired tool-point position
must therefore be converted to the corresponding TCP reference. At the
retained orientation, their rigid-body relation is

\begin{equation}
p_{\mathrm{Tool},d}(t)
=
p_d(t)+R_{\mathrm{EE,clearance}}r_{\mathrm{Tool,EE}}.
\label{eq:implementation_setup_rigid_body_relation}
\end{equation}

Solving this relation gives the desired TCP position \mbox{\(p_d(t)\)} as

\begin{equation}
p_d(t)
=
p_{\mathrm{Tool},d}(t)-R_{\mathrm{EE,clearance}}r_{\mathrm{Tool,EE}}.
\label{eq:implementation_setup_tcp_reference}
\end{equation}

During the linear part of the ramp, the desired TCP velocity is
\mbox{\(\dot p_d=-v_{\mathrm{set}}n_s\)}. It is zero after
\mbox{\(s_{\mathrm{set,max}}\)} is reached. The controller generates the press
by prescribing the selected tool-point trajectory and reconstructing the TCP
target that realises it. Because the surface restricts this commanded motion,
the resulting Cartesian position error generates the press. The configured
endpoint lies below the surface and therefore defines a spring reference
rather than an expected physical travel.

\mbox{\Cref{fig:setup_reference}} shows the complete construction from the
projected tool point to the TCP target.

\begin{figure}[H]
  \centering
  \input{figures/setup_reference.tex}
  \caption{Set-up reference generation for the selected tool point.}
  \label{fig:setup_reference}
\end{figure}

No time-varying tipping trajectory is commanded during set-up. The held
orientation reference acts as a finite-stiffness rotational spring
rather than as a rigid pose constraint, so finite rotational compliance permits
contact-induced end-effector rotation. When the virtual \abbr{CoC} is enabled,
the point-shifted matrices of
\mbox{\Cref{sec:self_alignment_virtual_center}} additionally couple the
translational press to the commanded moment; the same set-up position
reference is used in both cases.

The model-estimated external wrench supplied by libfranka is stored at the
clearance transition for the optional termination condition. After the
configured minimum duration, set-up can terminate when the estimated external
moment change exceeds the configured threshold, or through the independent
timeout. Every reported contact run terminated through the timeout, so that
threshold did not affect the reported results. With the pre-grinding gate
active, the controller remains in the set-up branch while waiting for operator
confirmation, and the coupled impedance stays active where it was selected.

The impedance acting on that reference changes at the same transition, from
the approach set to the contact set-up set. Three choices determine it: the
directional stiffness, the damping associated with those directions, and
whether the impedance reference point is the TCP or a shifted virtual
\abbr{CoC}. The controller constructs the directional gains first and applies
the compliance-centre transformation afterwards.

Directional Cartesian stiffness and damping are defined relative to the
surface frame and transformed to the robot base frame by the congruence of
\mbox{\Cref{sec:stiffness_damping_representation}}. Each phase of the sequence
activates its own gain set in the calibrated surface frame, and the set-up
translational frame remains configurable. Set-up and grinding draw on the same
source stiffness and damping blocks; the phase transition changes the generated
Cartesian reference and the choice between the coupled and decoupled branch. A phase gate can temporarily replace the active matrices with
dedicated hold gains while the current reference is maintained. The numerical
gains used in the experiments are given in \mbox{\Cref{ch:methodology}}.

For phase groups configured to use inertia-scaled damping, each directional
damping coefficient follows from the paired stiffness entry
\mbox{\(k_i\)} and the directional Cartesian inertia \mbox{\(\lambda_i(q)\)}
of the same translational or rotational direction:

\begin{equation}
d_i(q)
=
2\zeta\sqrt{\lambda_i(q)k_i},
\label{eq:implementation_inertia_scaled_damping}
\end{equation}

where \mbox{\(\zeta\)} is the configured directional damping factor. For a
single decoupled direction with \mbox{\(\zeta=1\)}, this is the
critical-damping coefficient of that local second-order model.

The directional inertia is evaluated from the current joint-space mass matrix
\mbox{\(M(q)\)} and Jacobian \mbox{\(J(q)\)} supplied by the libfranka model,
and then resolved along the axes of the active gain block. The inverse
\mbox{\(M(q)^{-1}\)} is never formed: an \mbox{\abbr{LDLT}} factorisation of
\mbox{\(M(q)\)} solves the corresponding linear system instead, and a small
regularisation term keeps the subsequent inversion conditioned. The result is
cached by phase group and recalculated when that group is entered again, so
the current robot configuration is reflected in the damping; configured
coefficient bounds, validity checks, and the fallback damping matrix are
recorded in \mbox{\Cref{app:controller_parameters}}.

The reported surface-contact sequence used inertia-scaled damping in the phase
groups stated in \mbox{\Cref{ch:methodology}}.

\label{sec:self_alignment_virtual_center}

The point-shift formulation derived in
\mbox{\Cref{sec:centre_of_compliance}} is implemented with the lever
\mbox{\(r_{c,0}=p_c-p_{\mathrm{TCP}}\)}. Two definitions are supported,
because the meaning of a fixed displacement depends on the frame that holds
it.

A tool-fixed displacement is configured in end-effector coordinates. Its
base-frame vector \mbox{\(r_{c,0}=R_{\mathrm{EE}}r_{c,\mathrm{EE}}\)} is
therefore updated from the measured end-effector orientation in every callback
and rotates as the end effector rotates. A surface-fixed displacement is
configured in surface coordinates, so
\mbox{\(r_{c,0}=R_{\mathrm{surface}}r_{c,S}\)} stays constant during set-up,
the surface frame being fixed for one controller session. The configuration
loader requires exactly one of the two definitions to be active when the
virtual centre is enabled, and rejects a parameter set selecting both or
neither. The two definitions are compared experimentally in
\mbox{\Cref{app:supporting_contact_checks}}.

The source translational and rotational matrices are assembled into
block-diagonal spatial gains at \mbox{\(p_c\)}, and the same congruence is
applied independently to stiffness and damping:

\begin{equation}
K_{\mathrm{TCP}}
=\operatorname{Ad}^\top(r_{c,0})K_c\operatorname{Ad}(r_{c,0}),
\qquad
D_{\mathrm{TCP}}
=\operatorname{Ad}^\top(r_{c,0})D_c\operatorname{Ad}(r_{c,0}).
\label{eq:implementation_shifted_impedance_matrices}
\end{equation}

For a tool-fixed displacement the shifted base-frame matrices are updated
whenever the measured end-effector orientation changes, whereas a
surface-fixed displacement leaves them constant as long as the source gains do
not change. Setting \mbox{\(r_{c,0}=0\)} makes the adjoint the identity and
returns the decoupled block-diagonal form.

During set-up this point-shifted impedance allows the commanded normal press
to contribute to the rotational response. The influence of the
compliance-centre position on that response is evaluated experimentally in
\mbox{\Cref{ch:results_discussion}}. The coupled branch is used only in the
controller modes configured for a virtual \abbr{CoC}; the cases that used it
are specified in \mbox{\Cref{ch:methodology}} and
\mbox{\Cref{app:controller_parameters}}.


\subsection{Grinding}
\label{subsec:implementation_grinding_phase}
\label{subsec:implementation_hold_guidance_modes}

After set-up, the grinding phase retains the normal press and superimposes a
smooth tangential motion using the decoupled impedance. No reported run entered
this phase; the experimental evaluation therefore ends at the pre-grinding
gate.


\section{Cartesian Pose Hold}
\label{subsec:implementation_pose_hold}
\label{sec:nullspace_conditioning_implementation}

Cartesian pose hold captures the current end-effector pose at its entry instant
\mbox{\(t_0\)} and uses the fixed references
\mbox{\(p_d=p_{\mathrm{EE}}(t_0)\)} and
\mbox{\(R_d=R_{\mathrm{EE}}(t_0)\)}. Its dedicated hold impedance is expressed
in the base frame. Surface approach, clearance detection and set-up reference
generation take no part in it, and its reported trials used fixed hold damping
rather than the inertia-scaled rule of
\mbox{\Cref{subsec:implementation_setup_phase}}.

Only the secondary torque varies inside this configuration. The four
selectable null-space configurations are shown in
\mbox{\Cref{fig:pose_hold_modes}}: no null-space torque, singular-value
conditioning, projected damping, and the two terms together. The Cartesian
reference and Cartesian impedance are unchanged between them.

\begin{figure}[H]
    \centering
    \input{figures/pose_hold_modes.tex}
    \caption{Cartesian pose hold with four selectable null-space configurations.}
    \label{fig:pose_hold_modes}
\end{figure}

The pose-hold study of \mbox{\Cref{sec:nullspace_hold_study}} compares four
settings under one internally commanded disturbance. These settings are no
null-space torque, projected damping, and singular-value conditioning at two
commanded magnitudes. They do not correspond to the four modes one for one.
The combined mode runs in the surface-contact sequence and was not compared in
pose hold. The disturbance, its timing and the evaluated quantities belong to
\mbox{\Cref{sec:nullspace_hold_study}}.

The implementation adds two choices not fixed by
\mbox{\Cref{sec:nullspace_svd}}. The pseudoinverse threshold is the configured
relative tolerance multiplied by the largest current singular value. The
resulting joint-torque projector is symmetrised numerically, and the same matrix
produces the recorded projected joint velocity
\mbox{\(\dot q_{\mathrm{null}}\)}. For singular-value conditioning, the
controller evaluates the Jacobian at
\mbox{\(q\pm\alpha_{\mathrm{probe}}v_7\)} and compares the smallest singular
value at each probe. This comparison uses the current robot transformations,
and no conditioning torque is requested inside the configured deadband. The
surface-contact sequence holds one combined setting throughout, so the
secondary controller is not a variable in those comparisons. Every numerical
value is given in \mbox{\Cref{ch:methodology}} and
\mbox{\Cref{app:controller_parameters}}.


\section{Robot-Side Safety and Command Handling}
\label{sec:collision_behavior_safety}
\label{subsec:robot_collision_configuration}
\label{subsec:initial_joint_posture}
\label{subsec:controller_exception_handling}

The joint-torque command of
\mbox{\Cref{eq:implementation_callback_torque_command}} is returned directly to
libfranka. No application-side saturation or torque-rate limiter is applied
after the Cartesian, null-space and Coriolis terms have been assembled, so the
configured collision and reflex monitoring is the independent protection layer
during the reported experiments. Its joint-torque and Cartesian-wrench
thresholds are recorded in
\mbox{\Cref{subsec:reproducibility_record}}. A robot communication,
motion-generation or torque-control error leaves the callback through
\mbox{\texttt{franka::Exception}} and ends the control session.

Everything the robot needs before torque control is completed before it starts:
the connection, error recovery, the collision configuration, the configuration
validation, the gripper action and the logging-buffer allocation. A libfranka
joint-motion generator then brings the robot to a configured initial joint
posture, or the run starts from a pose captured after manual guidance, with the
posture used in the reported experiments recorded in
\mbox{\Cref{app:controller_parameters}}. Operator input and file writing are
handled outside the real-time thread, so neither adds a blocking operation to
the joint-torque callback.


\section{Real-Time Data Recording}
\label{sec:recorded_signals}
\label{subsec:chronological_log_output}
\label{subsec:setup_run_evaluation}

Experimental signals are stored during torque control in a preallocated
in-memory ring buffer, so the callback performs no file access and grows no
buffer dynamically. Each sampled row carries the measured state, the active
reference, the calculated error and wrench, the controller phase, the
secondary-controller state, and the returned joint torque. When the allocated
capacity is reached the write index wraps and new rows replace the oldest, which
keeps the memory bounded while control continues. After the callback ends, the
retained samples are written to the \mbox{\abbr{CSV}} file in chronological
order.

Values captured at the clearance transition refer to the geometric event of
\mbox{\Cref{subsec:implementation_clearance_detection}}. The complete
column-level description is given in \mbox{\Cref{app:recorded_data}}, and the
experimental metrics calculated from these signals are defined in
\mbox{\Cref{ch:methodology}}.

\mbox{\Cref{ch:methodology}} next specifies the physical system, the
calibration procedure, the experimental parameter matrix, the contact
procedure, and the evaluation quantities used to assess this controller.
