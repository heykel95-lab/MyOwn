\chapter{Controller Design and Implementation}
\label{ch:implementation}

This chapter describes the implementation of the Cartesian impedance
controller used for the surface-grinding experiments. The implementation is
written in C++ with libfranka and Eigen and is evaluated in the \(1\,\mathrm{ms}\)
Franka Control Interface cycle. In addition to the Cartesian impedance law, the
software contains the surface and tool geometry, the approach--set-up--grind
state machine, the point-shifted coupled stiffness used during set-up, and the
SVD-based null-space controller.

\section{Real-Time Control Architecture}
\label{sec:implementation_scope}

The controller is divided into parameter handling, real-time control
mathematics, the phase machine, terminal interaction, and post-run reporting.
Five parameter files are merged at start-up. The first holds the common robot,
logging, surface, tool, gripper and null-space settings; the other four hold
collision thresholds, sequence settings, hold settings and manual-guidance
settings. No parameter file is read inside the real-time callback.

On every cycle the callback reads the measured robot state, updates the active
motion phase and its Cartesian reference, selects the phase-dependent gains,
and returns the task torque, null-space torque, and Coriolis term to libfranka.
\Cref{sec:control_impl} gives the order in which those operations are evaluated.
The experiment log is stored in a preallocated buffer, and file output is
performed after the control loop rather than in the \(1\,\mathrm{ms}\) callback.

With the active null-space mode, each callback evaluates one SVD of the current
Jacobian and two further SVDs at the two probe configurations. The probes also
require two additional calls to \texttt{model.zeroJacobian}. A full-rate
implementation trace contains \(11624\) rows over \(11.704\,\mathrm{s}\). Of the
adjacent callback timestamps, \(99.51\,\%\) are separated by exactly
\(1\,\mathrm{ms}\), and the effective delivered-callback rate is
\(993.1\,\mathrm{Hz}\). The active three-SVD law therefore ran sustainedly
within libfranka's nominal \(1\,\mathrm{kHz}\) torque interface.

Those timestamps do not establish a worst-case execution bound. They accumulate
the callback period supplied by libfranka and do not measure the callback's
local wall-clock execution time. The command success rate reported by the robot
is the fraction of the last 100 commands received successfully, which is neither
a callback-frequency nor an execution-time measurement, and it is not stored by
the current logger \citep{FrankaFCI2023}.

\section{Implemented Cartesian Impedance Controller}
\label{sec:state_model}

At the beginning of a control cycle, the joint configuration and velocity are
mapped from \texttt{franka::RobotState}. The end-effector pose reported by the
robot supplies the position
\(p_{\mathrm{EE}}\) and orientation
\(R_{\mathrm{EE}}\) of the configured libfranka end-effector frame in the robot
base frame. The implementation does not reconstruct this pose from a separate
DH model.

The geometric Jacobian is obtained with

\begin{lstlisting}[language=C++]
model.zeroJacobian(franka::Frame::kEndEffector, state)
\end{lstlisting}

and maps the measured joint velocity to the base-frame Cartesian velocity,

\begin{equation}
\begin{bmatrix}
\dot p_{\mathrm{EE}}\\
\omega_{\mathrm{EE}}
\end{bmatrix}
=J(q)\dot q .
\label{eq:software_cartesian_velocity}
\end{equation}

The controller uses the restoring position-error convention
\(e_p=p_d-p_{\mathrm{EE}}\). Its orientation error is obtained from the
current-to-desired relative rotation,

\begin{equation}
R_\Delta=R_{\mathrm{EE}}^\top R_d,
\qquad
e_R
=
R_{\mathrm{EE}}\,
\operatorname{Log}(R_\Delta)^\vee .
\label{eq:software_orientation_error}
\end{equation}

Thus \(e_R\) is the corrective axis--angle vector expressed in the base frame.
The decoupled Cartesian wrench is

\begin{equation}
F_{\mathrm{cmd}}
=
\begin{bmatrix}f\\m\end{bmatrix},
\qquad
\begin{aligned}
f&=K_p e_p+D_p(\dot p_d-\dot p_{\mathrm{EE}}),\\
m&=K_R e_R-D_R\omega_{\mathrm{EE}} .
\end{aligned}
\label{eq:software_decoupled_wrench}
\end{equation}

The wrench ordering is force followed by moment. Both quantities and the
end-effector Jacobian are expressed consistently in the base frame. The task
torque is therefore

\begin{equation}
\tau_{\mathrm{task}}
=
J^\top(q)F_{\mathrm{cmd}} .
\label{eq:software_task_torque}
\end{equation}

For all impedance-controlled phases, the returned command is

\begin{equation}
\tau_{\mathrm{cmd}}
=
J^\top(q)F_{\mathrm{cmd}}
+
\tau_{\mathrm{null}}
+
\tau_c(q,\dot q).
\label{eq:software_commanded_torque}
\end{equation}

The Coriolis vector is obtained from \texttt{model.coriolis(state)} and is
always added; it is not a run-time option. An explicit gravity vector is not
added because the Franka Control Interface compensates gravity internally in
external joint-torque mode \cite{FrankaFCI2023}. This follows the torque
structure of the official libfranka Cartesian impedance example
\cite{libfrankaCartesianExample}. Manual guidance is the one separate control
case: it returns \(\tau_c-d_{\mathrm{guide}}\dot q\) and bypasses the Cartesian
and null-space laws.

\section{SVD-Based Null-Space Control}
\label{sec:nullspace_conditioning_implementation}

The torque projector was constructed from the full \(6\times7\) geometric
Jacobian. For
\[
J=U\Sigma V^\top ,
\]
let \(\sigma_{\max}\) be the largest singular value and let
\(\rho\) be the configured relative tolerance. The cutoff is
\(\varepsilon_\rho=\rho\sigma_{\max}\), and the
truncated Moore--Penrose inverse used by the software is

\begin{equation}
J_\rho^+
=
\sum_{\sigma_i>\varepsilon_\rho}
\frac{1}{\sigma_i}v_i u_i^\top,
\qquad
N_\tau
=
\left(I-J_\rho^+J\right)^\top .
\label{eq:implementation_full_projector}
\end{equation}

Singular directions at or below the cutoff are omitted rather than inverted,
and the resulting \(N_\tau\) was symmetrised numerically to remove round-off
asymmetry. At full row rank, the seven-joint arm has a one-dimensional
kinematic null space; its unit direction was taken as the seventh column
\(\hat v_7=V(:,7)\).

A two-point probe method was used to determine the direction in which the
smallest singular value increased. The Jacobian was recomputed at two probe
configurations,

\begin{equation}
q_+=q+\alpha_{\mathrm{probe}}\hat v_7,
\qquad
q_-=q-\alpha_{\mathrm{probe}}\hat v_7.
\label{eq:implementation_sigma_probes}
\end{equation}

These two probes are the source of the two additional decompositions per cycle
reported in \cref{sec:implementation_scope}.

The selector \(s\in\{-1,0,+1\}\) points toward the probe with the larger
\(\sigma_{\min}\). The singular-value torque was suppressed when the sampled
difference remained within the configured deadband: if
\(\left|\sigma_{\min}(J(q_+))-\sigma_{\min}(J(q_-))\right|\) is not greater than
that deadband, \(s=0\). The probe distance \(\alpha_{\mathrm{probe}}\)
determines only where the two Jacobians are evaluated; it does not multiply the
commanded torque.

Four null-space control configurations were implemented. These comprised an
inactive mode, projected joint damping, a singular-value-based torque, and a
combination of the latter two terms. The four were provided so that the effects
of damping and of singular-value conditioning could be examined separately. The
selected mode determines the null-space torque as

\begin{equation}
\tau_{\mathrm{null}}
=
\begin{cases}
0,
& \text{off},\\[2pt]
-d_{\mathrm{null}}N_\tau\dot q,
& \text{null-space damping},\\[2pt]
k_\sigma N_\tau(s\hat v_7),
& \text{singular-value push},\\[2pt]
-d_{\mathrm{null}}N_\tau\dot q+k_\sigma N_\tau(s\hat v_7),
& \text{damping and singular-value push}.
\end{cases}
\label{eq:implementation_nullspace_torque}
\end{equation}

There is no return-to-start spring in the current implementation. Null-space
control is evaluated in hold, approach-orient, approach-descend, set-up, and
grind whenever the selected mode enables it. It is not switched off during the
approach and it is bypassed only in manual guidance. The combined configuration
(\texttt{nullspace\_mode=3}) was used in the experiments reported in the
following chapters, so projected joint damping and the switched sigma torque
remained active during set-up. The projector is Euclidean and kinematic rather
than dynamically consistent, and the sigma term is an active bias rather than a
dissipative one, so the secondary torque can influence the observed contact
motion.

The complete controlled torque remains

\begin{equation}
\tau_{\mathrm{cmd}}
=
J^\top(q)F_{\mathrm{cmd}}
+
\tau_{\mathrm{null}}
+
\tau_c .
\label{eq:implementation_final_torque_with_nullspace}
\end{equation}

The singular values were computed from the unscaled geometric Jacobian. Because
its translational and rotational rows have different physical units, the
reported \(\sigma_{\min}\) is an implementation-specific conditioning metric,
not a unit-invariant scalar.

\section{Surface and Tool Geometry}
\label{sec:surface_task_plane}

\subsection{Surface Task Frame}

The configured plane is

\begin{equation}
n_s^\top(p-p_s)=0,
\qquad
\|n_s\|=1,
\label{eq:given_surface_normal}
\end{equation}

where \(p_s\) and \(n_s\) are expressed in the robot base frame. In the current
software the normal is generated from tilts \(a\) about base \(x\) and \(b\)
about base \(y\):

\begin{equation}
n_s
=R_y(b)R_x(a)
\begin{bmatrix}0\\0\\1\end{bmatrix}
=
\begin{bmatrix}
\sin b\cos a\\
-\sin a\\
\cos b\cos a
\end{bmatrix}.
\label{eq:software_surface_normal_angles}
\end{equation}

An entered auxiliary tangent \(a_s\) is projected onto the plane and normalized,

\begin{equation}
t_1
=
\frac{a_s-n_s(n_s^\top a_s)}
{\|a_s-n_s(n_s^\top a_s)\|},
\label{eq:surface_tangent_x_axis}
\end{equation}

and the second tangent is

\begin{equation}
t_2=n_s\times t_1 .
\label{eq:surface_tangent_y_axis}
\end{equation}

The implementation stores the surface frame in the explicit column order

\begin{equation}
R_s=
\begin{bmatrix}
t_1&t_2&n_s
\end{bmatrix}.
\label{eq:software_surface_frame_order}
\end{equation}

The active parameter file sets \(a_s=[\,1,0,0\,]^\top\). With the active
surface tilts \(a=0^\circ\) and \(b=5^\circ\), this gives
\(t_1=[\,\cos5^\circ,0,-\sin5^\circ\,]^\top\) and
\(t_2=[\,0,1,0\,]^\top\). The names \texttt{tangent1} and
\texttt{tangent2} therefore refer to these two specific axes, not to an
interchangeable generic tangential direction.

Consequently, every parameter triple named
\texttt{tangent1/tangent2/normal} is stored as
\(\operatorname{diag}(k_{t_1},k_{t_2},k_n)\) before being rotated to the base
frame:

\begin{equation}
K_0
=
R_s
\operatorname{diag}(k_{t_1},k_{t_2},k_n)
R_s^\top .
\label{eq:software_surface_gain_transform}
\end{equation}

\subsection{Signed Tool-Axis Alignment}
\label{sec:tool_orientation_given_surface}

The surface frame and the desired tool orientation have different roles.
\(R_s\) defines gain and mask coordinates; it is not assigned directly as
\(R_d\). Let \(a_{\mathrm{EE}}\) be the configured physical tool axis in the
end-effector frame and let \(s_a\in\{-1,+1\}\) be the target sign. The required
axis in the base frame is

\begin{equation}
a_d=s_a n_s .
\label{eq:desired_tool_z_axis}
\end{equation}

For the grinding tool used here,
\(a_{\mathrm{EE}}=+z_{\mathrm{EE}}\) and \(s_a=-1\); hence the positive
end-effector \(z\)-axis is aligned with \(-n_s\), toward the surface.

This construction assumes that \(a_{\mathrm{EE}}\) is constant. In the
experimental hardware, however, the grinding tool can rotate relative to the
gripper by approximately \(\pm2^\circ\) about \(y_{\mathrm{EE}}\). The
controller has no sensor for this internal motion. Consequently,
\(R_{\mathrm{EE}}a_{\mathrm{EE}}\) is the tool axis inferred from the nominal
mounting transform; it is not an independent measurement of the physical
grinding-face axis while the tool moves in the gripper.

At the captured start orientation \(R_{\mathrm{start}}\), the initial physical
axis is \(a_0=R_{\mathrm{start}}a_{\mathrm{EE}}\). The code computes the minimum
rotation \(R_{\min}(a_0\rightarrow a_d)\) between these two unit vectors and
sets

\begin{equation}
R_d
=
R_{\min}(a_0\rightarrow a_d)R_{\mathrm{start}} .
\label{eq:desired_orientation_from_surface}
\end{equation}

This aligns the selected physical axis while changing the start-frame twist as
little as possible. The current orientation error is then

\begin{equation}
e_R
=
R_{\mathrm{EE}}\,
\operatorname{Log}\!\left(R_{\mathrm{EE}}^\top R_d\right)^\vee .
\label{eq:surface_orientation_error}
\end{equation}

The optional rotational mask uses the same
\([t_1,t_2,n_s]\) order:

\begin{equation}
e_{R,s}=R_s^\top e_R,
\qquad
e_R\leftarrow
R_s
\operatorname{diag}(\mu_{t_1},\mu_{t_2},\mu_n)e_{R,s},
\quad
\mu_i\in\{0,1\}.
\label{eq:surface_rotational_mask}
\end{equation}

Setting \(\mu_i=0\) removes the corresponding orientation-spring component. All
three mask entries were set to one for every reported run, so the tipping axes
are compliant because their rotational stiffness is low and not because their
orientation error is discarded. Once clearance is reached, set-up and grind
use the captured clearance orientation as \(R_d\).

For reference, an axis-aligned \(y\)-\(z\) plane has

\begin{equation}
n_s=
\begin{bmatrix}1&0&0\end{bmatrix}^\top .
\label{eq:yz_plane_surface_normal}
\end{equation}

The same implementation applies to an inclined plane because all geometry is
expressed through \(p_s\), \(n_s\), and \(R_s\).

\subsection{Rectangular Grinding Face and Clearance}
\label{sec:tool_contact_geometry}

The controlled contact geometry is a rectangular face attached to the
end-effector. If \(c_{\mathrm{EE}}\) is its centre and \(w_{\mathrm{EE}}\) and
\(\ell_{\mathrm{EE}}\) are its half-width and half-length vectors, its four
corners are

\begin{equation}
c_i
\in
\left\{
c_{\mathrm{EE}}\pm w_{\mathrm{EE}}\pm\ell_{\mathrm{EE}}
\right\}.
\label{eq:software_tool_face_corners}
\end{equation}

The descend direction is \(d=-n_s\). Before set-up, the code evaluates
\((R_{\mathrm{EE}}c_i)^\top d\) and selects the corners with the greatest
projection. Tied corners are averaged within a configurable tolerance.
Therefore the active controlled feature can be the face centre, an edge centre,
or a corner rather than an arbitrarily selected vertex. Its current base-frame
position is

\[
p_C=p_{\mathrm{EE}}+R_{\mathrm{EE}}c_C .
\]

Let
\[
\ell_{\mathrm{lead}}
=\max_i (R_{\mathrm{EE}}c_i)^\top d .
\]
The exact leading-corner height used for the clearance comparison is
\[
h_{\mathrm{lead}}
=n_s^\top(p_{\mathrm{EE}}-p_s)-\ell_{\mathrm{lead}} .
\]
Separately, the signed height of the averaged controlled feature is

\begin{equation}
h_C=n_s^\top(p_C-p_s).
\label{eq:signed_normal_distance}
\end{equation}

The corresponding point on the plane is

\begin{equation}
p_C^\Pi=p_C-h_Cn_s .
\label{eq:plane_projected_desired_position}
\end{equation}

During approach-descend the state transition is triggered when
\(h_{\mathrm{lead}}\) reaches the configured clearance. The averaged feature
\(p_C\) is used for control continuity and projection, but not for this exact
comparison. The two heights can differ by at most the configured
\(0.1\,\mathrm{mm}\) tie tolerance. This is a geometric transition. The
external-force estimate is available for diagnostics, but it is not used to
decide the transition.

At the transition the active feature, TCP pose, clearance orientation, and
external-wrench bias are frozen. With the signed set-up push coordinate
\(\delta_{\mathrm{push},0}=-h_C\), the desired feature position is continuous:

\begin{equation}
p_{C,d}(\delta_{\mathrm{push}})
=p_C^\Pi+\delta_{\mathrm{push}}(-n_s),
\qquad
p_{C,d}(\delta_{\mathrm{push},0})=p_C .
\label{eq:plane_projected_position_error}
\end{equation}

Increasing \(\delta_{\mathrm{push}}\) moves the selected feature into the surface along
\(-n_s\).

Let \(c_{C,\mathrm{EE}}\) denote the selected feature offset frozen in the
end-effector frame at clearance, and let
\(R_{\mathrm{clr}}=R_{\mathrm{contact,start}}\). The Cartesian position
reference supplied to the end-effector impedance is

\begin{equation}
p_{\mathrm{EE},d}
=
p_{C,d}-R_{\mathrm{clr}}c_{C,\mathrm{EE}} .
\label{eq:software_ee_target_from_feature}
\end{equation}

This conversion uses the frozen clearance orientation, not the live
\(R_{\mathrm{EE}}\). The current physical feature remains
\(p_C=p_{\mathrm{EE}}+R_{\mathrm{EE}}c_{C,\mathrm{EE}}\); therefore, if the
tool rotates during set-up, it need not coincide exactly with the constructed
feature reference \(p_{C,d}\).

There is one implementation-level hand-off caveat. In the callback that first
satisfies the clearance test, the phase variable is changed to
\texttt{set\_up} before gain selection, while the desired position and velocity
still contain that callback's approach values. The set-up gains and coupled
branch can therefore act on the old approach target for one sample; the
continuous target in \cref{eq:plane_projected_position_error} is generated on
the following callback. The first logged phase-2 row must not be treated as an
already settled set-up sample, and eliminating this one-cycle mismatch is a
recommended implementation correction.

\section{Phase-Dependent Gains and Automatic Damping}
\label{sec:surface_frame_gains}

The gain frames depend on the active phase:

\begin{itemize}
    \item approach-orient and approach-descend share translational and
    rotational gains specified in the surface frame
    \([t_1,t_2,n_s]\);
    \item set-up and grind use translational gains diagonal in base
    \([x,y,z]\), but rotational gains diagonal in
    \([t_1,t_2,n_s]\);
    \item hold uses isotropic base-frame translational and rotational gains; and
    \item an optional phase gate replaces the translational gains by a stiff,
    isotropic base-frame position lock while the run is paused.
\end{itemize}

When automatic damping is enabled, the controller obtains the joint-space mass
matrix \(M(q)\) on entry to a phase group, estimates the Cartesian inertia, and
caches the resulting damping for that group:

\begin{equation}
\Lambda
=
\left(
  \tfrac{1}{2}
  \left(JM^{-1}J^\top+
        \left(JM^{-1}J^\top\right)^\top\right)
  +10^{-9}I_6
\right)^{-1}.
\label{eq:software_cartesian_inertia}
\end{equation}

The estimate is rotated into the coordinate frame used by the relevant gain
block. For each diagonal direction \(i\), damping is selected as

\begin{equation}
d_i
=
2\zeta\sqrt{\Lambda_{ii}k_i},
\label{eq:software_auto_damping}
\end{equation}

subject to an optional manual per-axis floor and the configured upper bound of
\(8000\) in the corresponding damping unit. The floor is disabled in the current
parameter set, so the manual entries act as fallbacks rather than as lower
bounds.

Each damping block is evaluated in the coordinate frame of the gain block it
belongs to. During approach, both translational and rotational inertia are
expressed in the surface frame. During set-up and grind, translational inertia
is expressed in the base frame while rotational inertia remains in the surface
frame. Hold uses the base-frame inertia throughout and can fit one damping
factor towards the configured manual translational damping. At the pre-set-up
pause gate, separate scalar factors are fitted: translation targets the
configured gate-hold translational damping, and rotation targets the cached
approach rotational damping in the surface frame, there being no separate manual
pause-rotation target.

The estimate is accepted only after the factorisation, finiteness and positivity
of the required diagonal entries have been checked. An invalid estimate during
approach or set-up is recalculated on a later callback while that phase group
remains active. An invalid hold or pause-gate estimate instead latches the
manual fallback for that entry, and at the gate a failed estimate sends
translation to the gate-hold target and rotation to the cached or manual
approach damping. Disabling automatic damping selects the manual matrix
directly. The \(10^{-9}\) regularisation applies only to this mixed
translational--rotational task-inertia estimate and is distinct from the
relative SVD cutoff used for null-space projection.

\section{Compliance-Centre Coupling During Set-Up}
\label{sec:self_alignment_virtual_center}

The normal controller path uses the decoupled wrench of
\cref{eq:software_decoupled_wrench}. During the \texttt{set\_up} phase only, the
software can instead use a point-shifted \(6\times6\) stiffness and damping
matrix. The callback instantiates the point-shift law derived once in
\cref{sec:coupled_pole_stiffness}, using
\(K_c=\operatorname{diag}(K_p,K_R)\) and
\(D_c=\operatorname{diag}(D_p,D_R)\). With
\[
\Delta x=
\begin{bmatrix}e_p\\e_R\end{bmatrix},
\qquad
\Delta v=
\begin{bmatrix}\dot p_d-\dot p_{\mathrm{EE}}\\-\omega_{\mathrm{EE}}\end{bmatrix},
\]
the coupled set-up command is

\begin{equation}
F_{\mathrm{cmd}}
=K_{\mathrm{TCP}}\Delta x+D_{\mathrm{TCP}}\Delta v .
\label{eq:software_coupled_wrench}
\end{equation}

In the commanded-centre mode the centre of compliance is the frozen projected-clearance reference or the
live selected tool feature plus the configured base-frame XYZ offset. The
frozen source is the first-contact point, but it is captured
at geometric clearance rather than force contact. In the active configuration,
the centre of compliance is held constant from first contact, the TCP
reference is captured at
the same hand-off and the lever actually passed to the congruence is
\[
r_c=p_{\mathrm{TCP,clr}}-p_c .
\]
Consequently both \(p_c\) and \(r_c\) are constant throughout set-up; the live
option instead recomputes both references. The implementation can
alternatively use the unshifted block-diagonal matrix as a consistency check or
load previously saved full matrices. The coupled path is not active in grind:
grind shares the set-up gain values but returns to the decoupled wrench law.
This change is immediate. In the set-up callback that satisfies the exit
condition, the phase is assigned to \texttt{grind} before the wrench branch is
selected later in that same callback. That sample therefore already uses the
decoupled blocks. No interpolation is performed between
\(K_{\mathrm{TCP}},D_{\mathrm{TCP}}\) and the decoupled matrices. Although the
normal preload reference is continuous, the commanded wrench and
\(J^\top F_{\mathrm{cmd}}\) can therefore exhibit a step at the
transition.

The tool can still rotate under the physical edge-contact moment because the
tipping stiffnesses are compliant. The software does not prescribe a rotation
trajectory during set-up; it holds the captured clearance orientation as a soft
reference while pressing the selected feature.

\section{Control Phases}
\label{sec:control_phases}

The program can start either a stationary hold or the
approach--set-up--grind sequence. A separate manual-guidance start can be used
to place the robot before either choice.

\begin{enumerate}
    \item \textbf{Hold and manual guide.} Hold regulates the captured start pose
    with isotropic gains and the selected null-space mode. From hold, the user
    can enter manual guide, which commands Coriolis compensation and joint
    damping only. Recapturing stores the hand-moved pose and its wrench bias and
    resumes hold. Manual guidance can also be selected at start-up before the
    sequence begins.

    \item \textbf{Approach orient.} The TCP remains at the captured start
    position while the desired orientation minimally aligns the configured
    nominal tool axis with its signed target. The transition requires both the
    configured minimum time and a tool-axis angular error below the threshold.
    It does not require the complete orientation error to vanish.

    \item \textbf{Approach descend.} The TCP reference moves at the configured
    speed along \(-n_s\), subject to a maximum-distance guard. The active
    rectangular-face feature is reevaluated until the clearance is reached.
    The transition to set-up is based on the exact leading-corner height
    \(h_{\mathrm{lead}}\) defined above, not on the averaged-feature height
    \(h_C\) or estimated contact force.

    \item \textbf{Optional pre-set-up gate.} When enabled, reaching the
    clearance arms an Enter gate. A stiff position lock holds the actual pose,
    and the descend clock is frozen until the user continues.

    \item \textbf{Set-up.} The selected feature and clearance references are
    frozen. Its signed coordinate is ramped continuously from the captured
    value toward the configured set-up endpoint at the configured push speed.
    The orientation target remains the captured clearance orientation. The
    phase ends when the bias-subtracted external-moment norm exceeds its
    threshold after the minimum set-up time, or when the independent set-up
    timeout is reached. Force is logged but is not an exit condition. The
    point-shifted coupled law, when enabled, is applied only in this phase.

    \item \textbf{Optional pre-grind gate.} When enabled, the controller remains
    in set-up and continues evaluating its pressed reference until the user
    proceeds.

    \item \textbf{Grind.} The final set-up push is frozen as the grinding
    preload. The reference either executes a smooth back-and-forth sweep along
    \(t_1\) or \(t_2\), or holds only the normal penetration while allowing
    free tangential sliding. Grind uses the set-up gain values with the
    decoupled Cartesian law.
\end{enumerate}

All non-manual phases evaluate the selected null-space mode. The run terminates
when the configured experiment duration expires, when the user enters
\texttt{e} followed by Enter, when the descend maximum-distance guard is
reached, or when libfranka stops on a robot-side safety event.

\section{Franka Collision Behavior and Startup Handling}
\label{sec:collision_behavior_safety}

Before torque control starts, the program requests automatic error recovery,
applies the default Franka behaviour, and optionally installs the configured
joint-torque and Cartesian force/moment collision thresholds. The implementation
does not add separate clipping of the Cartesian wrench, null-space torque, or
torque rate; robot-side monitoring remains active.

The start-up menu can move the arm to the configured \(q_{\mathrm{init}}\), open
or grasp the tool with the Franka hand, enter manual guidance, and choose
between sequence and hold operation. The automatic gripper action is also
configurable: it may open the hand or grasp the tool, and it can retain an
already valid grasp rather than reopening the fingers. If the gripper action is
configured as mandatory, failure stops the run before the torque callback.

During start-up guidance and the in-loop manual-guide phase, the returned torque
is \(\tau_c-d_{\mathrm{guide}}\dot q\). The user may open or close the hand
during start-up guidance and then capture the current pose as the start of
sequence or hold operation.

\section{Logging and Post-Run Diagnostics}
\label{sec:software_logging}

The experiment log is a pre-sized ring buffer sampled every configured number of
control cycles. It records phase, null-space mode, measured and desired
positions, controlled feature and edge references, Cartesian errors and
velocities, commanded and estimated external wrenches, wrench biases, set-up
push, singular-value diagnostics, null-space torque magnitude, and commanded
joint torques.

The buffer is written to a comma-separated-values (\abbr{CSV}) file after the
control loop has exited, so the logger performs no file I/O in the real-time
callback.

\section{Complete Real-Time Callback}
\label{sec:control_impl}

The callback can be summarised as follows:

\begin{enumerate}
    \item Read \(q\), \(\dot q\), \(T_{\mathrm{EE}}\), the external estimates,
    and the contact indications.
    \item Obtain \(J(q)\), calculate \(J\dot q\), and update manual-guidance
    requests when applicable.
    \item Select the active rectangular-face feature and evaluate the phase
    transition and desired motion.
    \item Compute \(e_p\), the corrective base-frame \(e_R\), and the
    phase-specific automatic or fallback damping.
    \item Form either the decoupled wrench or the set-up-only coupled wrench.
    \item Compute the truncated-SVD null-space torque for the selected mode.
    \item Return
    \(J^\top F_{\mathrm{cmd}}+\tau_{\mathrm{null}}+\tau_c\).
    \item Copy the selected signals into the bounded in-memory log buffers.
\end{enumerate}

The core callback and supporting mathematical routines are reproduced in
Appendix~\ref{app:code}. The parameter values used for a particular run remain
separate from this control structure.

The controller described in this chapter is the one used for every run reported
below. \Cref{ch:methodology} documents the experimental campaign built on it:
the calibrated surface and tool geometry, the parameters held fixed, the four
quantities varied, and the metrics calculated from the logged signals.
