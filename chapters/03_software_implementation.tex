\chapter{Controller Design and Real-Time Implementation}
\label{ch:implementation}

This chapter describes the real-time implementation of the Cartesian impedance
controller developed in \mbox{\Cref{ch:theory}}. The implementation combines
surface-relative geometry, phase-dependent reference generation, a selectable
virtual \abbr{CoC}, null-space control, and real-time data handling.
Mathematical relations already established in \mbox{\Cref{ch:theory}} are
referenced here rather than restated, so that this chapter carries only what
the controller adds to them. The controller is written in C++ using libfranka
and Eigen and is executed through the Franka Control Interface
(\mbox{\abbr{FCI}}) at a nominal control period of \mbox{\(1\,\mathrm{ms}\)}.
Numerical settings used in the experiments are given in
\mbox{\Cref{ch:methodology}} and \mbox{\Cref{app:controller_parameters}}.


\section{Controller Architecture and Real-Time Control Cycle}
\label{sec:software_architecture}
\label{sec:real_time_control_loop}

The software separates configuration and operator interaction from the
real-time control calculation and from post-run data processing. The complete
parameter set is read and validated before a controller session starts, so the
real-time callback receives only the prepared configuration, preallocated
state, the robot-model interface, and non-blocking operator requests. File
output and run evaluation are performed after torque control has stopped.

At program start the \mbox{\abbr{FCI}} connection is established, error
recovery is requested, the selected collision behaviour is applied, and the
robot model is loaded. A separate keyboard thread receives operator requests
and transfers them through atomic variables, which keeps terminal input outside
the real-time callback. Reading and validating the configuration again before
each session permits settings to be changed between runs without recompiling.

\begin{figure}[H]
  \centering
  \resizebox{\textwidth}{!}{\input{figures/controller_block_diagram.tex}}
  \caption{Torque contributions combined in one control cycle.}
  \label{fig:controller_block_diagram}
\end{figure}

\mbox{\Cref{fig:controller_block_diagram}} shows the torque path of one
impedance-controlled cycle, and the order within that cycle is fixed. The
callback first reads the measured joint configuration \mbox{\(q\)}, the joint
velocity \mbox{\(\dot q\)}, the end-effector pose, the \mbox{\(6\times7\)}
geometric Jacobian \mbox{\(J(q)\)}, and the remaining robot-model quantities.
The phase logic then updates the desired Cartesian reference. The Cartesian
pose error and the impedance wrench \mbox{\(F=[f^\top,m^\top]^\top\)} are
evaluated according to \mbox{\Cref{subsec:cartesian_pose_error}} and
\mbox{\Cref{sec:cartesian_impedance_control}}, using the reference of the
active phase and the impedance matrices selected for it. That wrench is mapped
to joint torque through \mbox{\(J^\top(q)\)}, the secondary null-space torque
and the model Coriolis contribution are added, the required signals are stored
in preallocated memory, and the resulting torque vector is returned to
libfranka.

The end-effector pose supplied by the robot state is used directly for
\mbox{\(p_{\mathrm{EE}}\)} and \mbox{\(R_{\mathrm{EE}}\)}. The real-time
controller does not reconstruct that pose from a separate
Denavit--Hartenberg chain.

Two properties of the error evaluation belong to the implementation rather
than to the impedance law. A rotational mask can be applied by resolving
\mbox{\(e_R\)} in the surface frame, retaining the enabled components, and
transforming the result back to the base frame; the mask acts on the
rotational spring error alone, while the damping term continues to use the
measured angular velocity. The controller also carries two impedance branches,
one decoupled and one shifted to a virtual \abbr{CoC}, and the active phase
selects between them.

The complete impedance-controlled command is

\begin{equation}
\tau_{\mathrm{cmd}}
=
J^\top(q)F
+
\tau_{\mathrm{null}}
+
\tau_c(q,\dot q).
\label{eq:implementation_callback_torque_command}
\end{equation}

Here \mbox{\(\tau_{\mathrm{null}}\)} is the secondary null-space torque of
\mbox{\Cref{sec:nullspace_conditioning_implementation}} and
\mbox{\(\tau_c(q,\dot q)\)} is the Coriolis and centrifugal contribution
obtained from the libfranka model. No separate gravity term is added, because
the \mbox{\abbr{FCI}} compensates gravity for the external joint-torque
command, as described in \mbox{\Cref{subsec:coriolis_gravity_compensation}}. An
experiment-specific disturbance torque is added only for the null-space
pose-hold experiment of \mbox{\Cref{sec:nullspace_hold_study}} and is therefore
not part of the nominal controller formulation.


\section{Surface-Relative Geometry and Tool Representation}
\label{sec:surface_task_plane}

The contact sequence is formulated relative to the calibrated surface and to
the known geometry of the tool face. The controller therefore holds a surface
frame, a surface-relative tool orientation target, and a geometric reference
point on the rectangular face before the set-up impedance is applied.

\subsection{Surface Frame and Tool Orientation}
\label{subsec:implemented_surface_task_frame}
\label{sec:tool_orientation_given_surface}

The controller constructs the surface frame according to
\mbox{\Cref{subsec:surface_task_frame}} from a configured surface point
\mbox{\(p_s\)}, the surface orientation, and a configured first-tangent hint.
That hint is the in-plane reference direction of
\mbox{\Cref{subsec:surface_task_frame}} and is a parameter rather than a fixed
axis, so a fallback direction is applied when the configured one lies close to
\mbox{\(n_s\)}. The resulting directions
\mbox{\(t_1\)}, \mbox{\(t_2\)} and \mbox{\(n_s\)} are then used consistently
for the descent direction \mbox{\(-n_s\)}, the surface-relative orientation
command, the directional Cartesian gains, the compliance-centre definition
when a surface-fixed displacement is selected, and the surface-resolved
quantities of the experimental evaluation.

The tool normal is calibrated once in the end-effector frame. Its current
direction in the base frame follows from the measured end-effector
orientation:

\begin{equation}
n_{\mathrm{Tool},0}=R_{\mathrm{EE}}n_{\mathrm{Tool,EE}}.
\label{eq:implementation_current_tool_normal}
\end{equation}

Commanded angular offsets about the two surface tangents are combined into the
rotation vector

\begin{equation}
\theta_{\mathrm{tilt}}
=
\theta_{t_1}t_1
+
\theta_{t_2}t_2
\in\mathbb{R}^3.
\label{eq:implementation_tilt_rotation_vector}
\end{equation}

The magnitude of \mbox{\(\theta_{\mathrm{tilt}}\)} is the commanded offset
angle and its direction is the corresponding rotation axis, so the axis--angle
relation of \mbox{\Cref{eq:rodrigues_formula}} turns it directly into the
rotation matrix \mbox{\(R_{\mathrm{tilt}}\)}. This single vector covers the
conditions the experiments use: an offset about \mbox{\(t_1\)} alone, an offset
about \mbox{\(t_2\)} alone, and the intermediate tangent-plane directions.

Seating the tool face against the surface requires the tool normal to point
into the plane, so the flat target is the inward surface normal,

\begin{equation}
n_{\mathrm{flat}}
=
s_a n_s,
\qquad
s_a=-1,
\label{eq:implementation_flat_tool_axis}
\end{equation}

with \mbox{\(s_a\)} the configured tool-axis target sign. Applying the
commanded rotation to that axis gives the desired tool-normal direction,

\begin{equation}
n_d
=
R_{\mathrm{tilt}}n_{\mathrm{flat}}
=
R_{\mathrm{tilt}}\left(s_a n_s\right).
\label{eq:implementation_tool_normal_target}
\end{equation}

For a zero commanded offset the rotation is the identity and
\mbox{\(n_d=-n_s\)}. The shortest rotation that aligns the captured tool
direction with \mbox{\(n_d\)} is applied to the complete start orientation.
The implementation can additionally prescribe a twist about the desired tool
axis, which fixes the in-plane orientation of the rectangular face; because a
centred rectangle is unchanged by a half-turn, the equivalent orientation
closest to the captured start pose is selected. The settings used for the
measurements are stated in \mbox{\Cref{ch:methodology}}.


\subsection{Tool Geometry and Selected Contact Point}
\label{sec:tool_contact_geometry}

The tool face is represented as a rectangle fixed in the end-effector frame.
Its centre offset, half-width vector, and half-length vector define the four
vertices

\begin{equation}
\left\{
r_{\mathrm{face,EE}}
\mathbin{\pm}r_{\mathrm{width,EE}}
\mathbin{\pm}r_{\mathrm{length,EE}}
\right\}.
\label{eq:implementation_tool_face_vertices}
\end{equation}

From that geometry the controller determines the point expected to reach the
surface first. This point is the selected tool point
\mbox{\(p_{\mathrm{Tool}}\)}, used as the contact reference during set-up.
Depending on the tool orientation it is a leading corner, the midpoint of a
leading edge, or the tool-face centre. Its position follows from the
end-effector-frame offset \mbox{\(r_{\mathrm{Tool,EE}}\)},

\begin{equation}
p_{\mathrm{Tool}}=p_{\mathrm{TCP}}+R_{\mathrm{EE}}r_{\mathrm{Tool,EE}},
\label{eq:implementation_contact_point_position}
\end{equation}

where the tool centre point coincides with the reported end-effector origin in
this implementation, \mbox{\(p_{\mathrm{TCP}}=p_{\mathrm{EE}}\)}.

Three points have to be kept apart here. \mbox{\(p_{\mathrm{TCP}}\)} is the
Cartesian reference point the impedance law regulates.
\mbox{\(p_{\mathrm{Tool}}\)} is physical tool geometry, and its base-frame
offset
\mbox{\(r_{\mathrm{Tool}}=R_{\mathrm{EE}}r_{\mathrm{Tool,EE}}=p_{\mathrm{Tool}}-p_{\mathrm{TCP}}\)}
changes with the tool orientation. The virtual \abbr{CoC}
\mbox{\(p_c\)} of \mbox{\Cref{sec:centre_of_compliance}} is a
software-defined point carrying no tool geometry at all, and moving it does not
move \mbox{\(p_{\mathrm{Tool}}\)}.

\begin{figure}[H]
  \centering
  \input{figures/face_feature_selection.tex}
  \caption{Tool face geometry and the selected leading feature.}
  \label{fig:face_feature_selection}
\end{figure}

During tool orientation and surface approach the four vertices are transformed
to the base frame and compared along the descent direction, as
\mbox{\Cref{fig:face_feature_selection}} shows. The vertex with the largest
projection is geometrically closest to the surface. Vertices whose projected
positions agree within the configured tie tolerance are grouped and averaged,
so a general orientation selects a leading corner, two nearly equal
neighbouring corners define a leading edge, and four nearly equal corners
define the face centre.

The clearance of the foremost face point and the height of the averaged
controlled point serve different purposes. The foremost-face clearance
determines the transition from approach to set-up, while the averaged point is
the reference for the subsequent set-up motion. At the clearance transition the
implementation stores the selected tool-point offset in the end-effector frame,
its projection onto the calibrated surface, the measured TCP pose, and the
orientation that will be held during set-up. The selected offset is then kept
constant for the whole of set-up.


\section{Phase-Dependent Cartesian Impedance}
\label{sec:surface_frame_gains}

Three choices determine the active Cartesian impedance: the directional
stiffness, the damping associated with those directions, and whether the
impedance reference point is the TCP or a shifted virtual \abbr{CoC}.
The controller constructs the directional gains first and applies the
compliance-centre transformation afterwards.

\subsection{Directional Stiffness and Damping}
\label{subsec:phase_dependent_gain_construction}
\label{subsec:inertia_scaled_damping_calculation}

Directional Cartesian stiffness and damping are defined relative to the
surface frame and transformed to the robot base frame by the congruence of
\mbox{\Cref{sec:stiffness_damping_representation}}. Each controller phase
activates its own gain set. Surface-related phases use the calibrated surface
frame, Cartesian pose hold expresses them in the base frame, and the set-up
translational
frame remains configurable. Set-up and grinding draw on the same source
stiffness and damping blocks; what the phase transition changes is the
generated Cartesian reference and the choice between the coupled and decoupled
branch. A phase gate can temporarily replace the active matrices with
dedicated hold gains while the current reference is maintained. The numerical
gains used in the experiments are given in \mbox{\Cref{ch:methodology}}.

For phase groups configured to use inertia-scaled damping, each directional
damping coefficient follows from the paired stiffness entry
\mbox{\(k_i\)} and the directional Cartesian inertia \mbox{\(\lambda_i(q)\)}
of the same translational or rotational direction:

\begin{equation}
d_i(q)
=
2\zeta\sqrt{\lambda_i(q)k_i},
\label{eq:implementation_inertia_scaled_damping}
\end{equation}

where \mbox{\(\zeta\)} is the configured directional damping factor. For a
single decoupled direction with \mbox{\(\zeta=1\)}, this is the
critical-damping coefficient of that local second-order model.

The directional inertia is evaluated from the current joint-space mass matrix
\mbox{\(M(q)\)} and Jacobian \mbox{\(J(q)\)} supplied by the libfranka model,
and then resolved along the axes of the active gain block. The inverse
\mbox{\(M(q)^{-1}\)} is never formed: an \mbox{\abbr{LDLT}} factorisation of
\mbox{\(M(q)\)} solves the corresponding linear system instead, and a small
regularisation term keeps the subsequent inversion conditioned. The result is
cached by phase group and recalculated when that group is entered again, so
the current robot configuration is reflected in the damping; configured
coefficient bounds, validity checks, and the fallback damping matrix are
recorded in \mbox{\Cref{app:controller_parameters}}.

The reported surface-contact sequence used inertia-scaled damping in the phase
groups stated in \mbox{\Cref{ch:methodology}}. Standard Cartesian pose hold is
a separate case: its reported null-space trials used fixed hold damping
instead.


\subsection{Virtual Centre of Compliance}
\label{sec:self_alignment_virtual_center}

The point-shift formulation derived in
\mbox{\Cref{sec:centre_of_compliance}} is implemented with the lever
\mbox{\(r_{c,0}=p_c-p_{\mathrm{TCP}}\)}. Two definitions are supported,
because the meaning of a fixed displacement depends on the frame that holds
it.

A tool-fixed displacement is configured in end-effector coordinates. Its
base-frame vector \mbox{\(r_{c,0}=R_{\mathrm{EE}}r_{c,\mathrm{EE}}\)} is
therefore updated from the measured end-effector orientation in every callback
and rotates as the end effector rotates. A surface-fixed displacement is
configured in surface coordinates, so
\mbox{\(r_{c,0}=R_{\mathrm{surface}}r_{c,S}\)} stays constant during set-up,
the surface frame being fixed for one controller session. The configuration
loader requires exactly one of the two definitions to be active when the
virtual centre is enabled, and rejects a parameter set selecting both or
neither. Which definition holds a displacement is examined experimentally in
\mbox{\Cref{app:supporting_contact_checks}}.

The source translational and rotational matrices are assembled into
block-diagonal spatial gains at \mbox{\(p_c\)}, and the same congruence is
applied independently to stiffness and damping:

\begin{equation}
K_{\mathrm{TCP}}
=\operatorname{Ad}^\top(r_{c,0})K_c\operatorname{Ad}(r_{c,0}),
\qquad
D_{\mathrm{TCP}}
=\operatorname{Ad}^\top(r_{c,0})D_c\operatorname{Ad}(r_{c,0}).
\label{eq:implementation_shifted_impedance_matrices}
\end{equation}

For a tool-fixed displacement the shifted base-frame matrices are updated
whenever the measured end-effector orientation changes, whereas a
surface-fixed displacement leaves them constant as long as the source gains do
not change. Setting \mbox{\(r_{c,0}=0\)} makes the adjoint the identity and
returns the decoupled block-diagonal form.

During set-up this point-shifted impedance allows the commanded normal press
to contribute to the rotational response. The influence of the
compliance-centre position on that response is evaluated experimentally in
\mbox{\Cref{ch:results_discussion}}. The coupled branch is used only in the
controller modes configured for a virtual \abbr{CoC}; the cases that used it
are specified in \mbox{\Cref{ch:methodology}} and
\mbox{\Cref{app:controller_parameters}}.


\section{Contact Sequence and Reference Generation}
\label{sec:control_phases}

The main run sequence passes through tool orientation, surface approach,
set-up, and grinding, in that order. The orientation phase can be omitted by
configuration, and optional operator gates can hold the current reference
between phases. Standard Cartesian pose hold, set-up-impedance hold, and
manual guidance are separate operator modes.

  \caption{Run phase sequence and Cartesian pose hold.}
  \label{fig:phase_flow_chart}
\end{figure}

\mbox{\Cref{fig:phase_flow_chart}} summarises the implemented phase flow.


\subsection{Orientation and Surface Approach}
\label{subsec:implementation_tool_orientation_phase}
\label{subsec:implementation_surface_approach_phase}

The tool-orientation phase holds the captured start position while the desired
orientation is advanced towards the surface-relative target of
\mbox{\Cref{eq:implementation_tool_normal_target}}, following a rate-limited
interpolation from the captured start orientation. Its transition is evaluated
from the tool-axis error and, when the in-plane twist is enabled, the
remaining spin error about the target tool axis. A configured minimum duration
prevents immediate acceptance of a transient orientation, and a timeout
supplies an alternative transition path. The orientation reached at the end of
this phase becomes the reference used during approach.

During surface approach the desired position advances from the captured start
position along \mbox{\(-n_s\)} with a rate limit and a maximum travel. The
rectangular tool geometry is evaluated continuously, so the controller always
knows which corner or edge currently has the smallest geometric clearance. The
transition to set-up occurs when that foremost-face clearance reaches the
configured geometric threshold, which is a geometric criterion rather than a
force-detected contact event.

At the clearance transition the selected tool point is held constant, and the
controller stores its projected surface point, the current TCP pose, and the
orientation reference. With the optional pre-set-up gate enabled, the captured
pose is held until operator confirmation and the set-up references are then
captured from the current measured state. Reaching the maximum permitted
approach distance before the clearance threshold is satisfied terminates the
approach.


\subsection{Contact Set-Up}
\label{subsec:implementation_setup_phase}

Set-up generates the contact press that the experiments evaluate. At the
clearance transition the selected tool point is projected onto the calibrated
plane, giving the starting reference \mbox{\(p_{\mathrm{Tool},0}\)}. The scalar
coordinate \mbox{\(s_{\mathrm{set}}(t)\)} describes the commanded displacement
of that point from \mbox{\(p_{\mathrm{Tool},0}\)} towards the surface. It
advances at the configured press speed \mbox{\(v_{\mathrm{set}}\)} from the
clearance transition at \mbox{\(t_{\mathrm{set},0}\)}. From
\mbox{\(t_{\mathrm{set,max}}\)}, the instant the ramp reaches the configured
endpoint \mbox{\(s_{\mathrm{set,max}}\)}, the coordinate is held there:

\begin{equation}
s_{\mathrm{set}}(t)
=
\begin{cases}
s_{\mathrm{set}}(t_{\mathrm{set},0})
+v_{\mathrm{set}}\left(t-t_{\mathrm{set},0}\right),
& t_{\mathrm{set},0}\leq t<t_{\mathrm{set,max}},\\[4pt]
s_{\mathrm{set,max}}, & t\geq t_{\mathrm{set,max}}.
\end{cases}
\label{eq:implementation_setup_press_coordinate}
\end{equation}

The ramp starts from the signed surface coordinate of the selected tool point
rather than from zero. That start value is negative, because the tool point
still stands above the plane at the clearance transition.
The commanded reference therefore begins at the measured tool-point position
and enters set-up without a step. \mbox{\Cref{app:controller_parameters}}
records the configured press speed and endpoint. The desired position of the
selected tool point is therefore

\begin{equation}
p_{\mathrm{Tool},d}(t)
=
p_{\mathrm{Tool},0}-s_{\mathrm{set}}(t)n_s.
\label{eq:implementation_setup_face_point_reference}
\end{equation}

The impedance law regulates the TCP rather than the tool point, so this
desired tool-point position has to be converted into the corresponding desired
TCP position. Expressing the stored tool-point offset in the base frame at the
orientation \mbox{\(R_{\mathrm{clr}}\)} captured at the clearance transition
gives \mbox{\(r_{\mathrm{Tool,clr}}=R_{\mathrm{clr}}r_{\mathrm{Tool,EE}}\)},
and the two desired positions are related by that same rigid-body offset.
Solving for the TCP reference gives

\begin{equation}
p_d(t)
=
p_{\mathrm{Tool},d}(t)-R_{\mathrm{clr}}r_{\mathrm{Tool,EE}}.
\label{eq:implementation_setup_tcp_reference}
\end{equation}

The controller therefore does not push the TCP into the surface. It prescribes
where the selected tool point should move and reconstructs the TCP target that
realises it. Because the surface restricts the commanded motion of the tool
point, the resulting Cartesian position error generates the press.
\mbox{\Cref{fig:setup_reference}} shows that construction. The commanded
endpoint lies below the surface, so the configured endpoint sets a spring
reference rather than a distance the tool was expected to travel.

\begin{figure}[H]
  \centering
  \input{figures/setup_reference.tex}
  \caption{Set-up reference generation for the selected tool point.}
  \label{fig:setup_reference}
\end{figure}

The desired orientation remains equal to the orientation captured at the
clearance transition. No time-varying tipping trajectory is commanded during
set-up. That held reference acts as a finite-stiffness rotational spring
rather than as a rigid pose constraint, so finite rotational compliance permits
contact-induced end-effector rotation. When the virtual \abbr{CoC} is enabled,
the point-shifted matrices of
\mbox{\Cref{sec:self_alignment_virtual_center}} additionally couple the
translational press to the commanded moment; the same set-up position
reference is used in both cases.

The model-estimated external wrench supplied by libfranka is stored at the
clearance transition for the optional termination condition. After the
configured minimum duration, set-up can terminate when the estimated external
moment change exceeds the configured threshold, or through the independent
timeout. Every reported contact run terminated through the timeout, so that
threshold did not affect the reported results. With the pre-grinding gate
active, the controller remains in the set-up branch while waiting for operator
confirmation, and the coupled impedance stays active where it was selected.


\subsection{Auxiliary and Post-Set-Up Modes}
\label{subsec:implementation_grinding_phase}
\label{subsec:implementation_hold_guidance_modes}
\label{subsec:implementation_run_termination}

A subsequent grinding phase is implemented by maintaining the normal set-up
reference while superimposing a smooth tangential motion along a selected
surface tangent. This phase returns to the decoupled impedance formulation. It
was not entered in the reported experiments and is therefore not discussed
further.

Three operator modes sit outside the run sequence. Standard Cartesian pose hold
regulates a captured pose with the dedicated hold impedance. Set-up-impedance
hold applies the set-up gain construction and can retain the virtual
\abbr{CoC}.
Manual guidance applies joint damping together with the model Coriolis
contribution before the required references are captured again.

A controller session ends when the configured duration expires, an operator
stop is requested, the maximum approach distance is exceeded, or libfranka
terminates the motion because of a robot-side event. File writing and post-run
evaluation occur only after the real-time callback has finished.


\section{SVD-Based Null-Space Implementation}
\label{sec:nullspace_conditioning_implementation}

The Cartesian impedance defines the primary task. The Panda retains one
joint-space degree of freedom when the \mbox{\(6\times7\)} task Jacobian has
full row rank, and the null-space formulation of
\mbox{\Cref{sec:nullspace_svd}} is evaluated inside each
impedance-controlled callback.

For every cycle the full singular value decomposition of \mbox{\(J(q)\)} is
evaluated. The relative \mbox{\abbr{SVD}} tolerance is multiplied by the
largest current singular value to obtain the threshold used in the
Moore--Penrose pseudoinverse; singular directions above the threshold are
inverted and the remaining reciprocal entries are set to zero. The resulting
joint-torque null-space projector \mbox{\(N_\tau\)} is symmetrised
numerically. For the Moore--Penrose construction used here the orthogonal
projector is symmetric, so \mbox{\(N_\tau=N_q\)} analytically; the
implementation applies the symmetrised \mbox{\(N_\tau\)} both to the secondary
torque and to the recorded projected joint velocity.

Four secondary-torque modes are selectable: disabled, projected damping alone,
singular-value conditioning alone, and their sum,

\begin{equation}
\tau_{\mathrm{null}}
=
-d_{\mathrm{null}}N_\tau\dot q
+
k_\sigma N_\tau\left(s_\sigma v_7\right).
\label{eq:implementation_nullspace_torque}
\end{equation}

Singular-value conditioning determines \mbox{\(s_\sigma\)} by sampling the
current redundant right-singular direction \mbox{\(v_7\)} in both signs. Two
nearby joint configurations are formed at
\mbox{\(q\pm\alpha_{\mathrm{probe}}v_7\)}, their Jacobians are evaluated using
the current robot transformations, and the smallest singular values at the two
sampled configurations are compared. If their difference exceeds the
configured deadband, the sign associated with the larger
\mbox{\(\sigma_{\min}\)} is selected; within the deadband no conditioning
torque is requested. The selected direction is projected again through
\mbox{\(N_\tau\)} before the torque is returned, which keeps the commanded
contribution in the numerical null space defined by the current pseudoinverse.

The contact experiments use one fixed combined null-space setting, so the
secondary controller does not become a variable of those comparisons. The
individual null-space terms are examined separately in the pose-hold
experiment of \mbox{\Cref{sec:nullspace_hold_study}}, and the corresponding
numerical settings are given in \mbox{\Cref{ch:methodology}} and
\mbox{\Cref{app:controller_parameters}}.


\section{Real-Time Operation, Safety, and Data Recording}
\label{sec:collision_behavior_safety}
\label{subsec:robot_collision_configuration}
\label{subsec:initial_joint_posture}
\label{subsec:controller_exception_handling}

Robot preparation, operator interaction, and file handling are arranged so
that none of them adds a blocking operation to the joint-torque callback.
Robot connection, error recovery, collision configuration, configuration
validation, gripper preparation, and logging-buffer allocation are all
completed before torque control begins. The robot can then be moved to a
configured initial joint posture through a libfranka joint-motion generator,
or the operator can start from a pose captured after manual guidance; the
posture used in the reported experiments is recorded in
\mbox{\Cref{app:controller_parameters}}. Operator input and file writing are
handled outside the real-time thread, and a robot communication,
motion-generation, or torque-control error exits the callback through
\mbox{\texttt{franka::Exception}}.

The joint-torque command of
\mbox{\Cref{eq:implementation_callback_torque_command}} is returned directly to
libfranka. No application-side saturation or torque-rate limiter is applied
after the Cartesian, null-space, and Coriolis terms have been assembled, so the
configured collision and reflex monitoring remains an independent robot-side
protection mechanism.


\subsection{Real-Time-Safe Data Recording}
\label{sec:recorded_signals}
\label{subsec:chronological_log_output}
\label{subsec:setup_run_evaluation}

The signals required for post-run analysis are stored in a bounded in-memory
ring buffer whose memory is allocated before torque control starts, so the
callback never grows the log dynamically. Each sampled row contains the
measured state, the active reference, the calculated error and wrench, the
controller phase, the secondary-controller state, and the returned joint
torque. When the allocated capacity is reached, the write index wraps and new
samples replace the oldest rows, which keeps the memory use bounded during
real-time control. After the callback ends, the ring-buffer contents are
written in chronological order to the \mbox{\abbr{CSV}} file.

Values captured at the clearance transition refer to the geometric event of
\mbox{\Cref{subsec:implementation_surface_approach_phase}}. The complete
column-level description is given in \mbox{\Cref{app:recorded_data}}, and the
experimental metrics calculated from these signals are defined in
\mbox{\Cref{ch:methodology}}.

\mbox{\Cref{ch:methodology}} next specifies the physical system, the
calibration procedure, the experimental parameter matrix, the contact
procedure, and the evaluation quantities used to assess this controller.
